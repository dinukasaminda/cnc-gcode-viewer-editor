 Yes. What you want is not just a G-code path viewer; it is a **PCB material-removal simulator** that reconstructs what the copper-clad board should look like after the `.nc` file runs.

## Build prompt

> Build a web-based **3D PCB CNC G-code Simulator and Final Result Previewer**.
>
> The main purpose is to load one or more GRBL `.nc` / `.gcode` files generated by FlatCAM and show the **expected final physical PCB**, rather than only drawing G-code movement lines.
>
> The simulator must model a copper-clad PCB as real stock consisting of:
>
> - Copper top layer
> - FR4 substrate underneath
> - Configurable PCB width, height and thickness
> - Configurable copper thickness
>
> Parse the G-code and simulate actual material removal from the board.
>
> ### Primary use cases
>
> Support three PCB machining operations:
>
> 1. **Isolation milling**
>    - 30° V-bit
>    - configurable V-tip diameter, such as 0.1 mm
>    - configurable V-angle
>    - cutting width must change automatically according to Z depth
>    - show removed copper and exposed FR4
>
> 2. **Drilling**
>    - cylindrical PCB drill bits
>    - configurable drill diameter
>    - holes must visibly pass through the PCB when the commanded Z depth exceeds board thickness
>
> 3. **Board cutout**
>    - cylindrical/end-mill cutters
>    - configurable cutter diameter
>    - simulate multiple-depth passes
>    - display the resulting PCB outline and tabs if present
>
> ### V-bit geometry
>
> For a V-bit, calculate the effective cutting diameter from:
>
> **effectiveDiameter = tipDiameter + 2 × depth × tan(angle / 2)**
>
> where depth is the positive magnitude below the stock surface.
>
> Example:
>
> - tip diameter = 0.1 mm
> - angle = 30°
> - Z = -0.10 mm
>
> The resulting groove should be approximately 0.154 mm wide.
>
> The simulation must use the changing V-bit diameter along the toolpath rather than treating the tool as a fixed cylinder.
>
> ### G-code support
>
> Support common GRBL/FlatCAM commands including:
>
> - G0 rapid movement
> - G1 linear cutting movement
> - G2 / G3 arcs
> - G17 XY plane
> - G20 inches
> - G21 millimeters
> - G90 absolute positioning
> - G91 relative positioning
> - G54 work coordinate system
> - feedrate F
> - spindle command M3 / M4
> - spindle stop M5
> - S spindle value
> - comments
> - repeated/modal coordinates
>
> Maintain modal G-code state correctly.
>
> ### 3D final-result rendering
>
> Use WebGL, preferably Three.js.
>
> The main view must render the board as a realistic PCB:
>
> - copper-colored top surface
> - FR4-colored material where copper has been milled away
> - physically visible drilled holes
> - physically visible cutout edges
> - realistic V-shaped isolation grooves
>
> The most important display mode is **Final PCB**, showing only the expected board after machining.
>
> Also provide optional views:
>
> - Final PCB
> - Toolpaths
> - Final PCB + toolpaths
> - Copper removal only
> - Depth heatmap
> - Top view
> - Perspective 3D view
>
> Rapid moves should never remove material.
>
> ### Stock settings
>
> Allow the user to configure:
>
> - PCB width
> - PCB height
> - PCB thickness, default 1.6 mm
> - copper thickness, default 0.035 mm
> - stock X origin
> - stock Y origin
> - stock Z surface, normally Z = 0
>
> Also provide **Auto Detect Bounds From G-code**.
>
> Add configurable margin around the detected job.
>
> ### Tool configuration
>
> Each CNC job must have a tool definition.
>
> Tool types:
>
> - V-bit
> - cylindrical end mill
> - drill
>
> V-bit parameters:
>
> - tip diameter
> - included angle
> - shank diameter
>
> End-mill parameters:
>
> - diameter
>
> Drill parameters:
>
> - diameter
>
> Do not confuse the V-bit's 3.175 mm shank diameter with its cutting diameter.
>
> ### Multiple G-code files
>
> Allow multiple files to be loaded into one PCB project, for example:
>
> - `pcb_isolation.nc`
> - `pcb_drill.nc`
> - `pcb_cutout.nc`
>
> Apply all operations to the **same virtual PCB stock** so the user sees the complete final board.
>
> Each file should have an individually configurable tool.
>
> Users must be able to toggle each operation on/off.
>
> ### Simulation controls
>
> Include:
>
> - Play
> - Pause
> - Stop
> - Restart
> - simulation speed
> - step through commands
> - jump to final result
>
> While simulating, show:
>
> - current G-code line
> - X
> - Y
> - Z
> - feedrate
> - spindle state
> - active tool
> - percentage complete
>
> ### Validation
>
> Analyze the G-code before simulation and show warnings for:
>
> - cutting outside stock
> - unexpected negative X/Y
> - toolpath exceeding machine limits
> - cutting too deeply
> - missing spindle-start command
> - rapid G0 move below PCB surface
> - plunge feed that appears excessive
> - missing units
> - unsupported G-code
> - tool diameter larger than narrow PCB features
>
> ### Measurement tools
>
> Add interactive measuring tools so the user can click the final PCB and measure:
>
> - trace width
> - isolation gap
> - hole diameter
> - distance between holes
> - PCB dimensions
> - cut depth
>
> Display measurements in millimeters.
>
> ### Precision
>
> PCB features can be very small, so do not use a low-resolution voxel grid that makes 0.1–0.2 mm traces inaccurate.
>
> Target useful geometry resolution around **0.01–0.025 mm** for PCB isolation where practical.
>
> Use an efficient representation such as:
>
> - 2D height field for isolation milling
> - polygon/boolean geometry for copper removal
> - analytical tool sweeps
> - adaptive-resolution mesh generation
>
> rather than generating millions of unnecessary 3D voxels.
>
> ### Performance
>
> Large G-code files may contain hundreds of thousands of movements.
>
> Parse and process them in a Web Worker so the interface stays responsive.
>
> Simplify collinear paths where doing so does not change machining geometry.
>
> Generate the final mesh efficiently rather than rebuilding the entire PCB for every G-code instruction.
>
> ### UI
>
> Create a clean engineering-style interface:
>
> **Left panel**
>
> - loaded G-code files
> - tools
> - stock settings
>
> **Center**
>
> - large interactive 3D PCB preview
>
> **Right panel**
>
> - simulation information
> - warnings
> - measurements
>
> **Bottom**
>
> - playback timeline
> - current G-code line
>
> Support orbit, pan, zoom and Reset View.
>
> ### Most important acceptance test
>
> Given FlatCAM isolation G-code produced for a:
>
> - 0.1 mm tip
> - 30° V-bit
> - Cut Z = -0.10 mm
>
> the simulator must visually produce isolation grooves approximately **0.154 mm wide**, expose the substrate beneath the removed copper, and leave the remaining copper traces visible.
>
> The user should be able to look at the final 3D model and understand approximately **what the finished PCB will physically look like before sending the G-code to the CNC**.

## Core architecture

I would structure it like this:

| Component | Responsibility |
|---|---|
| G-code parser | Convert G-code into normalized movements |
| Modal-state engine | Track G90/G91, units, feed, coordinates, etc. |
| Tool engine | V-bit, drill and end-mill geometry |
| Stock model | Copper + FR4 |
| Material-removal engine | Calculate areas/depth removed |
| PCB renderer | Build final 3D mesh |
| Toolpath renderer | Optional movement visualization |
| Validator | Detect dangerous/suspicious G-code |
| Measurement engine | Measure final PCB features |
| UI | Files, tools, simulation and 3D controls |

### Important implementation choice

I would **not** start with full volumetric 3D CNC simulation.

PCB machining is mostly a **2.5D problem**, so a much faster design is to maintain a high-resolution **surface/height representation plus copper mask**:

**G-code → swept cutter footprint → update surface depth → determine whether copper remains → generate final 3D mesh**

That will make your application dramatically faster while still accurately representing PCB isolation.

For example, a V-bit pass can conceptually produce:

**Copper surface → V-shaped channel → exposed FR4 → remaining copper trace → V-shaped channel → copper**

That is the difference between the tool you're building and something like Candle: **Candle primarily shows where the tool travels; your software should show what material remains after the tool has traveled.**
